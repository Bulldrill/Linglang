LinLang

Un lenguaje donde no hay clases, ni objetos, ni siquiera "números" sueltos — solo espacios vectoriales, vectores, y transformaciones lineales entre ellos. El mismo modelo describe una tabla de tareas, un qubit, y la migración de ese qubit a otra máquina.

🧠 Memoria y estructuras

Qué pasa de verdad cuando escribís let — sin magia, con Go debajo.

¿Qué es LinLang?

LinLang es un lenguaje interpretado, de tipado dinámico-por-espacio, construido sobre una idea única: cada dominio de datos es un espacio vectorial, cada entidad es un vector, y cada regla de negocio es una transformación lineal (o casi-lineal) entre espacios. No hay clases ni herencia — hay espacios (space) y las funciones puras entre ellos (transform, func).

La extensión LinLang/Q lleva esa misma idea a la mecánica cuántica: un espacio de Hilbert (hilbert) es, matemáticamente, un espacio vectorial sobre ℂ en vez de ℝ — así que toda la maquinaria del lenguaje (declarar el espacio, construir un vector dentro de él, transformarlo) se reutiliza sin cambios. No es una integración ni un plugin: es el mismo núcleo, instanciado sobre otro cuerpo numérico.

Por qué esto importa en la práctica

No hay dos lenguajes, uno clásico y otro cuántico atados con una API. space y hilbert comparten runtime, comparten persistencia, comparten el mismo Vector por debajo. Aprender la mitad clásica de esta guía es aprender el 80% de la mitad cuántica.

Instalación y primer programa

LinLang se distribuye como un único binario de Go (sin runtime externo, sin dependencias del sistema más allá de lo que tu programa use — SQLite y Redis son opcionales y solo se activan si pedís persistencia).

bash
# clonar y compilar
git clone https://github.com/Bulldrill/Linglang.git
cd Linglang
go build -o linlang .

# correr un archivo .lin
./linlang examples/ejemplo.lin

# o entrar al REPL interactivo
./linlang -i

Tu primer programa — tres líneas, sin main, sin import:

saludo.lin
space Personas: edad: Real, ingresos: Real
let p1 = Personas[25, 40000]
print p1
salida[✔️] Espacio creado: Personas dims=[edad ingresos] types=[Real Real] [✔️] Vector p1 creado en espacio Personas [25 40000] [📌] p1 = [25 40000] (espacio: Personas)

No hay una llamada a "crear instancia" separada de la declaración del tipo: Personas[25, 40000] es la construcción del vector, literal, igual que [25, 40000] sería un array en otro lenguaje — solo que acá el array sabe a qué espacio pertenece.

El modelo mental

Tres ideas cargan todo el lenguaje. Si las internalizás, el resto de esta guía es vocabulario.

1. Un espacio es un tipo, pero un tipo es solo una lista de dimensiones nombradas

.lin
space Tarea: id: Real, prioridad: Real, estado: Real, categoria: Real

Esto no crea una clase con métodos. Crea un core.Space — básicamente {Name: "Tarea", Dimensions: ["id","prioridad","estado","categoria"]} — y a partir de ahí, Tarea[1, 3, 0, 1] es un punto en ℝ⁴. "Una tarea" no es un objeto con comportamiento propio; es una posición en un espacio de 4 dimensiones.

2. Una regla de negocio es una función entre dos puntos en espacios (quizás distintos)

.lin
transform completar: Tarea x Tarea -> Tarea {
    id        = p.id
    prioridad = p.prioridad
    estado    = 2
    categoria = p.categoria
}

"Completar una tarea" no es tarea.completar() mutando algo. Es una función Tarea × Tarea → Tarea — toma el estado actual (p) y un vector delta (m, acá sin usar) y produce un vector nuevo. Nada se muta nunca; ver Memoria y estructuras para por qué eso es literal, no una metáfora.

3. Un qubit es exactamente la misma idea, sobre ℂ

.lin
hilbert Qubit: dim 2
let psi = ket(Qubit, 0.6, 0.8)
let girado = apply(H_Qubit, psi)

hilbert declara un espacio igual que space (con amplitudes complejas en vez de componentes reales); apply es un transform restringido a ser unitario. No hay un segundo lenguaje acá — es core.Space y core.Transform con un cuerpo numérico distinto. Esta es, literalmente, la contribución central del proyecto: ver LinLang/Q.

Construí tu primera app: un gestor de tareas

Vamos a construir, de punta a punta, la misma aplicación que vive en examples/todo.lin + cmd/todo-server: un backend de tareas con prioridad, estado y categoría, persistido de verdad, expuesto por HTTP. El objetivo es que veas cómo encajan space, transform, persist y query en un programa real, no en ejemplos sueltos.

Paso 1 — el espacio del dominio

todo.lin
# id        — identificador único
# prioridad — 1=baja  2=media  3=alta
# estado    — 0=pendiente  1=en_progreso  2=completada
# categoria — 1=trabajo  2=personal  3=urgente
space Tarea: id: Real, prioridad: Real, estado: Real, categoria: Real

Una decisión de diseño real acá: los estados y categorías son enteros codificados como Real, no un tipo enum. Esto es deliberado — mantiene todo el espacio en ℝ⁴, lo que significa que norm(), dot() y el centroide del espacio (ver stats) siguen siendo operaciones válidas sobre tareas completas, no solo sobre sus campos numéricos "de verdad".

Paso 2 — las transiciones como transforms

todo.lin
transform completar: Tarea x Tarea -> Tarea {
    id        = p.id
    prioridad = p.prioridad
    estado    = 2
    categoria = p.categoria
}

transform priorizar: Tarea x Tarea -> Tarea {
    id        = p.id
    prioridad = m.prioridad
    estado    = p.estado
    categoria = p.categoria
}

Notá el patrón: completar ignora m por completo (fuerza estado = 2, un valor constante) — es una transición de estado. priorizar en cambio lee m.prioridad — usa el segundo vector como portador del valor nuevo, un patrón de "delta". Ambos son la misma construcción sintáctica; la diferencia es solo qué dimensiones del body referencian m.

Paso 3 — crear, persistir, consultar

.lin
let t1 = Tarea[1, 3, 0, 1]
persist t1

let t = query_one Tarea where id == 1
let t_new = completar(t, t)
persist t_new

let urgentes = query Tarea where prioridad == 3 and estado != 2

Con LINLANG_DB=memory:// (o sin configurar nada — es el default) esto vive solo en RAM del proceso. Cambiá la variable de entorno a sqlite://linlang.db o redis://localhost:6379/0 y el programa no cambia una línea — ver Backends de persistencia.

Paso 4 — exponerlo por HTTP

El patrón de cmd/todo-server es el que vale la pena internalizar: cada endpoint HTTP no contiene lógica de negocio en Go — genera un fragmento de código .lin y lo corre en un Runtime fresco.

go
// PUT /tasks/{id}/complete
code := fmt.Sprintf(
    "let t = query_one Tarea where id == %.0f\n"+
    "let t_new = completar(t, t)\n"+
    "persist t_new",
    float64(id),
)
rt := parser.NewRuntime()
rt.SetStore(db)
rt.Parse(code)
writeJSON(w, 200, rt.Vectors["t_new"])

Go es la "carcasa": parsea HTTP, serializa JSON. Toda la regla de negocio — qué significa "completar", qué prioridades son válidas, cómo se calcula el centroide del espacio — vive en .lin, y se puede cambiar sin recompilar el servidor. Corré el ejemplo real:

bash
LINLANG_DB=redis://redis:6379/0 docker compose up --build
curl -s -X POST localhost:8080/tasks -H "Content-Type: application/json" \
  -d '{"title":"Comprar pan","priority":3,"category":1}'
curl -s localhost:8080/tasks/stats | python3 -m json.tool
Núcleo clásico

El lenguaje

Todo lo que no es cuántico ni distribución. Si ya leíste el modelo mental, esta sección es, en gran parte, llenar los detalles de sintaxis.

Espacios — space

space <nombre>: <dim>: <tipo>, <dim>: <tipo>, ...

Declara un espacio vectorial nombrado. Cada dimensión tiene un nombre y un tipo opcional (Real si se omite — ver Tipos). Un espacio es, en Go, exactamente esto:

core/spaces.go
type Space struct {
    Name       string
    Dimensions []string
    Types      []DimType // paralelo a Dimensions; Real por defecto
}

No hay métodos, no hay validación más allá del número de componentes en el literal. Redeclarar un espacio con el mismo nombre simplemente sobreescribe la entrada en Runtime.Spaces — no hay protección contra eso, es responsabilidad del programa.

.lin
space Personas: edad: Real, ingresos: Real, energia: Real
space Tarea: id: Real, titulo: String, prioridad: Real

Vectores y literales

Espacio[v₁, v₂, ..., vₙ]

Un literal de vector es el nombre del espacio seguido de sus componentes entre corchetes, en el mismo orden que las dimensiones declaradas. El número de valores debe coincidir exactamente con len(Dimensions) — si no coincide, core.NewVector hace panic (es uno de los pocos lugares del runtime que no falla "suave").

.lin
let p1 = Personas[25, 40000, 0.8]
let t1 = Tarea[1, "comprar pan, leche y huevos", 3]

Un string entre comillas dobles es válido en cualquier posición cuya dimensión sea String (ver abajo) — incluso con comas adentro: el parser es consciente de comillas y no corta el string en la coma interna.

Cada vector tiene una identidad propia, independiente de su contenido:

ID
int64 — autoincremental, global al proceso (no por espacio, no por Runtime). Es el contador vectorIDCounter en core/vectors.go.
Space
puntero al *Space del que es instancia.
Values
[]float64 — un slice de Go, del mismo largo que las dimensiones.
El ID no es la primera dimensión

El ID autoincremental (v.ID) y la dimensión que el programa llama id (v.Values[0]) son cosas distintas que suelen confundirse. Si tu espacio declara una dimensión literalmente llamada id, las expresiones p.id dentro de un transform leen esa dimensión, no el contador interno — el contador solo se usa como fallback si no existe ninguna dimensión con ese nombre. Ver Expresiones aritméticas.

Tipos: Real y String

LinLang tiene exactamente dos tipos de dimensión. No hay enteros, booleanos, ni tipos definidos por el usuario más allá de un space entero.

TipoRepresentación en GoParticipa en aritméticaUso típico
Real defaultfloat64Sí — add, dot, norm, scale, projectmagnitudes, contadores, enums codificados
Stringstring, en un mapa aparteNo — excluida de toda operación vectorialtítulos, etiquetas, metadata

Internamente, una dimensión String no ocupa un slot real en aritmética: su posición en Values queda en 0 (sin usar), y el valor de verdad vive en Vector.Strings map[string]string, indexado por nombre de dimensión. Esto es lo que te permite llamar norm(t1) sobre una tarea con título sin que el texto "contamine" la magnitud:

.lin
space Tarea: id: Real, titulo: String, prioridad: Real
let t1 = Tarea[1, "comprar pan", 3]
let n = norm(t1)  # = sqrt(1² + 3²) — "titulo" no participa

Las columnas String se persisten de verdad: SQLite las mapea a columnas TEXT, Redis guarda el literal (no un float formateado), y MemoryStore guarda ambos lados. query/filter soportan igualdad sobre String (==, !=) — ver multi-condición.

Inferencia de tipos

Si omitís el nombre del espacio en un literal, el runtime lo infiere por aridad: busca, entre todos los espacios declarados, cuál tiene exactamente esa cantidad de dimensiones.

.lin
space Personas: edad: Real, ingresos: Real, energia: Real
space Mascotas: edad: Real, especie: Real

let p1 = [25, 40000, 0.8]  # infiere Personas (3 dims)
let m1 = [3, 1]            # infiere Mascotas (2 dims)
salida[🔮] p1: tipo inferido = Personas (3 dimensiones) [🔮] m1: tipo inferido = Mascotas (2 dimensiones)

Si ningún espacio tiene esa aridad, o si más de uno la comparte, la inferencia no adivina — reporta un error capturable (TypeInferenceError, ver manejo de errores) nombrando los candidatos ambiguos en vez de elegir uno arbitrariamente.

Operaciones vectoriales nativas

Cinco funciones integradas, todas sobre el mismo core.Vector. Ninguna muta su argumento — Add/Scale/Project siempre devuelven un vector nuevo (ver por qué).

FunciónFirmaDevuelveComplejidad
add(v1, v2)mismo espaciovector nuevo, componente a componenteO(d)
scale(v, k)k: literal o escalar ligadovector nuevo, cada componente × kO(d)
dot(v1, v2)mismo espacioescalar (producto interno euclídeo)O(d)
norm(v)—escalar (magnitud L2)O(d)
project v onto Espaciosintaxis especial, no fn(...)vector en el espacio destino; dimensiones sin coincidencia quedan en 0O(d₁·d₂)
.lin
let suma      = add(p1, p2)
let escalado  = scale(p1, 2)
let similitud = dot(p1, p2)
let magnitud  = norm(p1)
let perfil    = project p1 onto Perfil

Transforms

transform <nombre>: <Dom1> x <Dom2> -> <Codominio> { <dim> = <expr> ... }

Una función binaria pura entre espacios: recibe dos vectores (p del primer dominio, m del segundo) y produce uno nuevo en el codominio, una línea por dimensión de salida.

.lin
transform adoptar: Personas x Mascotas -> Adopciones {
    persona_id = p.id
    mascota_id = m.id
    compat     = p.energia * m.edad / 10
}
let a1 = adoptar(p1, m1)

Cada dim = expr es evaluada independientemente — no hay return, no hay flujo de control dentro del body, solo una expresión aritmética por dimensión de salida (ver Expresiones). Si una dimensión del codominio no aparece en el body, queda en 0.

Funciones — func

func <nombre>: <Dominio> -> <Codominio> { <dim> = <expr> ... }

La contraparte unaria de transform: un solo dominio, llamada con un solo argumento. No es un concepto nuevo en el runtime — es, literalmente, un transform cuyo segundo dominio es nil, reutilizando toda la maquinaria existente (las expresiones m.dim ya devolvían 0 cuando m es nil, así que no hizo falta ningún caso especial para soportar esto).

.lin
func doblar: Personas -> Personas {
    id      = p.id
    energia = p.energia * 2
}
let p2 = doblar(p1)

Expresiones aritméticas

El cuerpo de un transform/func usa un mini-lenguaje de expresiones: literales numéricos, + - * / con la precedencia usual, paréntesis, menos unario, y acceso a campos p.dim / m.dim.

p.dim
lee la dimensión dim del primer argumento. Si dim no existe en el espacio de p, evalúa a 0 (no es un error).
m.dim
igual, para el segundo argumento. Si m es nil (llamada a un func unario), cualquier m.dim evalúa a 0.
p.id / m.id
caso especial: si el espacio no declara una dimensión llamada id, cae al contador autoincremental Vector.ID en vez de a 0. Si el espacio sí declara id, esa dimensión gana — ver el callout en Vectores.

División por cero evalúa a 0 en vez de propagar Inf/NaN — una elección deliberada para que una regla de negocio con un divisor ocasionalmente nulo no envenene silenciosamente el resto del cálculo con NaN.

Condicionales — when

when <lhs> <op> <valor>:
    <accion>(<vector>)

when no es un if de bloque — es una guarda de una sola condición que registra una acción diferida, ejecutada en la siguiente línea no vacía. El lado izquierdo acepta varias formas:

Forma de LHSEjemploSignificado
vec.dima1.compatdimensión de un vector clásico
nombre de escalarsimilitudcualquier valor en Scalars (resultado de dot, norm, purity, ...)
purity(rho)—pureza de una matriz de densidad
qnorm(psi)—norma de un estado cuántico
count(coleccion)—tamaño de una colección

Operadores: > < >= <= == !=.

.lin
when a1.compat >= 0.2:
    approve(a1)

Colecciones

Una colección ([]*core.Vector en Go) nace de query, filter o map, y vive en Runtime.Collections. Tres operaciones de primera clase:

Iteración — for

for <var> in <coleccion> { <sentencias> }

Liga var a cada vector de la colección, por turno, y corre el cuerpo completo para cada uno. El cuerpo puede contener cualquier sentencia válida a nivel de programa — no hay un sub-lenguaje restringido para el body.

.lin
for t in urgentes {
    print t
    let n = norm(t)
}
Límite conocido

El cuerpo de un for no puede contener otro bloque con llaves (gate, transform, otro for) — el recolector de líneas solo rastrea el par de llaves más externo. No afecta a ningún programa de ejemplo actual, pero es una limitación real del parser, no una regla del lenguaje.

Filtrado — filter

filter(<coleccion>, <dim> <op> <valor> [and|or ...])

A diferencia de query (que solo puede filtrar contra el store, ver Persistencia), filter opera enteramente en memoria sobre una colección ya cargada — por eso puede comparar dimensiones String por igualdad, algo que query no soporta.

.lin
let hogar = filter(todas, categoria == "hogar")
let urgentes = filter(todas, prioridad == 3 and estado == 0)

Transformación — map

map(<coleccion>, <transform>, <vector-fijo>)

Aplica un transform ya registrado a cada vector de la colección, contra un segundo vector fijo — consistente con que los transforms de LinLang modelan relaciones binarias, no funciones unarias de colección (para eso está func combinado con for).

.lin
let resultados = map(personas, adoptar, m1)  # adoptar(p, m1) para cada p

Indexado

<coleccion>[i]

Acceso por posición, 0-indexado. Fuera de rango reporta un error capturable (IndexOutOfRange) en vez de hacer panic.

.lin
let primero = resultados[0]

Manejo de errores — try/catch

try { <sentencias> }
catch <Nombre> { <sentencias> }

El cuerpo del try corre línea por línea y se detiene en la primera que reporte un error capturable. Si el nombre del error coincide con la cláusula catch (o esta viene vacía), corre el body del catch; si no coincide, se reporta el desajuste y no se "traga" el error silenciosamente. Si el try tiene éxito completo, el catch nunca corre.

.lin
try {
    let t = query_one Tarea where id == 99
}
catch NotFound {
    let fallback = Tarea[0, 0]
}

No todo error del intérprete es capturable — solo un subconjunto deliberado de condiciones de runtime (no de sintaxis) está conectado:

NombreSe dispara en
NotFoundquery_one sin resultados; project/dot/norm/scale/add con un vector inexistente; llamada a func/transform con un argumento inexistente
IndexOutOfRangeindexado de colección fuera de rango
TypeInferenceErrorinferencia de tipo ambigua o sin coincidencias
ImportErrorinclude de un archivo inexistente o ilegible

Un error de sintaxis (una línea mal formada) nunca es capturable — es un bug del programa, no una condición de la que tenga sentido "recuperarse".

Módulos — include

include "ruta/al/archivo.lin"

Lee y parsea el archivo en el mismo Runtime — no es una importación con namespace propio, es literalmente como si pegaras el contenido del archivo ahí. Las rutas se resuelven relativas al directorio de trabajo del proceso, no al archivo que incluye.

Incluir el mismo archivo dos veces (directo, o a través de un ciclo A→B→A) es un no-op silencioso la segunda vez — el runtime rastrea qué rutas ya cargó.

.lin
include "schema.lin"
let t1 = Tarea[1, 3]  # Tarea viene de schema.lin

REPL interactivo

bash
./linlang -i
# o: ./linlang repl

Un Runtime persistente, alimentado una línea a la vez. Lo interesante no es la interfaz — es que no hizo falta escribir ningún buffer especial para el REPL: los bloques multi-línea (transform, gate, for, try) ya rastrean su propio estado entre llamadas a ParseLine (ver Bloques multi-línea), así que tipear un transform a lo largo de varias líneas del prompt funciona exactamente igual que en un archivo. El prompt cambia a ... mientras estás dentro de un bloque abierto.

El REPL conecta el store vía LINLANG_DB igual que todo-server, así que persist/query funcionan interactivamente también.

Capa de persistencia

Persistencia transparente

Guardar un vector no debería requerir que el programa sepa si va a SQLite, Redis o memoria. En LinLang, no lo requiere.

persist / drop / query / query_one

SentenciaEfecto
persist vupsert de v en el backend configurado, por la primera dimensión como clave
drop velimina del backend y del runtime
let x = query Espaciocarga todos los vectores del espacio → Runtime.Collections["x"]
let x = query Espacio where dim op val [and/or ...]igual, filtrado
let x = query_one Espacio where dim op valprimer resultado → Runtime.Vectors["x"] (no una colección)
.lin
let t1 = Tarea[1, 3, 0, 1]
persist t1

let todas = query Tarea
let t = query_one Tarea where id == 1
drop t1

Multi-condición en where

and liga más fuerte que or — precedencia booleana estándar: a and b or c es (a and b) or c, nunca a and (b or c).

.lin
let urgentes = query Tarea where prioridad == 3 and estado == 0
let mix      = query Tarea where prioridad == 1 or categoria == 1
query vs. filter

query pasa el filtro al store.Backend, que solo entiende []float64 — por diseño, nunca va a poder comparar una dimensión String por igualdad. Si necesitás eso, cargá la colección completa con query (sin where, o con un filtro parcial) y refiná con filter, que sí opera sobre el *Vector completo. Ver Colecciones.

Backends: memoria, SQLite, Redis

Un único DSN en la variable de entorno LINLANG_DB decide el backend. El programa .lin no cambia una línea entre uno y otro.

DSNImplementaciónNotas
memory:// defaultstore.MemoryStoremapa en RAM, protegido con sync.RWMutex — se pierde al terminar el proceso
sqlite://archivo.dbstore.SQLiteStoreuna tabla por espacio, creada al primer persist; columnas REAL o TEXT según el tipo de dimensión; vía modernc.org/sqlite (Go puro, sin cgo)
redis://host:puerto/dbstore.RedisStorecada vector = un Hash (linlang:{Espacio}:{id}), más un Set de índice (linlang:{Espacio}:_ids) para poder iterar todos

Las tres implementan la misma interfaz chica:

store/store.go
type Backend interface {
    Upsert(space *core.Space, values []float64, strs map[string]string) error
    Query(space *core.Space, filter func([]float64) bool) ([]*core.Vector, error)
    Delete(space *core.Space, id float64) error
    Close() error
}

Esquema generado automáticamente: space Tarea: id: Real, prioridad: Real, ... es semánticamente equivalente a CREATE TABLE "Tarea" ("id" REAL PRIMARY KEY, "prioridad" REAL NOT NULL DEFAULT 0, ...) — nunca escribís DDL a mano.

Extensión cuántica

LinLang/Q

Todo lo de El lenguaje, instanciado sobre ℂⁿ. Un hilbert es un space; un ket es un vector; una gate es un transform restringido a ser unitario. La diferencia es el cuerpo numérico, no el modelo.

Espacios de Hilbert — hilbert

hilbert <nombre>: dim <n>
.lin
hilbert Qubit: dim 2
hilbert QReg2: dim 4

Declarar un espacio de dimensión 2 o 4 auto-registra las puertas estándar para esa dimensión — no hace falta escribirlas a mano:

dimPuertas auto-registradas
cualquieraI_<nombre> (identidad)
2H_<nombre>, X_<nombre>, Y_<nombre>, Z_<nombre>
4CNOT_<nombre>

Estados — ket

ket(<Espacio>, amp₀, amp₁, ...)

Construye core.QuantumState — una lista de amplitudes complejas ([]complex128) atadas a un *HilbertSpace. Las amplitudes aceptan notación compleja: 0.5, 0.5i, 0.5+0.5i, -0.5-0.5i.

.lin
let ket0 = ket(Qubit, 1, 0)                 # |0⟩
let psi  = ket(Qubit, 0.6, 0.8)              # estado arbitrario normalizado

No hay normalización automática — si pasás amplitudes cuya suma de cuadrados no da 1, el estado queda así; Norm()/Normalize() existen como operaciones explícitas en core/hilbert.go pero no hay un builtin de lenguaje que las exponga directamente (se usan internamente, p. ej. en teleport).

Puertas — gate

gate <nombre>: <Dominio> -> <Codominio> { row [...] ... }

Declarás la matriz fila por fila; al cerrar el bloque, el runtime verifica U†U = I (unitariedad) con tolerancia 10⁻⁹ y te avisa si no se cumple — pero no rechaza la puerta, solo lo marca en el log. Es responsabilidad del programa no usar una puerta no-unitaria.

.lin
gate MiH: Qubit -> Qubit {
    row [0.7071067811865476,  0.7071067811865476]
    row [0.7071067811865476, -0.7071067811865476]
}
salida[✔️] Gate 'MiH' registrada [✓ unitaria]

Combinar puertas sin declarar la matriz a mano: kron(g1, g2) (producto de Kronecker — ver abajo).

apply, tensor, measure, shots

apply(gate, estado) → estado

Producto matriz-vector U|ψ⟩, delegado al QuantumBackend activo (ver Backends) — no siempre es álgebra local; depende de qué technology esté seleccionada.

tensor(ψ1, ψ2) → estado en el espacio producto

Producto de Kronecker de las amplitudes; el espacio producto se crea (o reutiliza) automáticamente con dimensión dim(H1) × dim(H2).

measure(ψ) → entero clásico

Determinista — devuelve el argmax de |αᵢ|², no un muestreo real. Esto es deliberado, para que los ejemplos y tests sean reproducibles. Para muestreo real, usá shots.

shots(ψ, n) → histograma

Muestrea n veces de la distribución de Born de verdad (vía CDF inversa), y devuelve un map[int]int de conteos — el mismo formato que usarían resultados de hardware real.

.lin
let ket0 = ket(Qubit, 1, 0)
let plus = apply(H_Qubit, ket0)
let m    = measure(plus)        # determinista: siempre el mismo resultado
let hist = shots(plus, 1000)    # ~500/500, varía cada corrida

Teleportación — teleport

teleport(<estado>)

No es un ejemplo de laboratorio — es una primitiva real del runtime. teleport(psi) abre un QuantumChannel efímero, comparte un par de Bell, corre el protocolo completo (CNOT + H + medición + corrección de Bob), y te devuelve el estado migrado — exactamente igual al original, sin haber transmitido jamás el qubit físico.

.lin
hilbert Qubit: dim 2
let psi = ket(Qubit, 0.6, 0.8)
let bob = teleport(psi)   # bob.Amplitudes == psi.Amplitudes, exacto
salida[✔️] bob = teleport(psi) bits_clásicos=(m0=0, m1=0) probs=[0.36 0.64]
Por qué esto, y no simplemente copiar

El teorema de no-clonación prohíbe duplicar un estado cuántico arbitrario desconocido. "Migrar" un qubit —a otra variable, a otro nodo— no puede ser una copia; tiene que ser teleportación, el único mecanismo físicamente consistente. Es la razón de ser de toda la capa de distribución. Desarrollo completo en Arquitectura interna y en la monografía, capítulo "Teleportación como Primitiva de Infraestructura".

Restricción: solo definida para 1 qubit (dim(Espacio) == 2) — intentarlo sobre un registro mayor da un error claro, no un resultado incorrecto.

Por debajo del capó

Arquitectura interna

Esta sección existe para que nunca tengas que decir "no sé cómo funciona mi propio lenguaje". Sin asumir que sabés Go, ni gestión manual de memoria, ni nada de eso.

Cómo se ejecuta un programa

LinLang no tiene las fases que esperarías de un lenguaje "de verdad": no hay un árbol de sintaxis (AST) que se construye primero y se recorre después, no hay bytecode, no hay una pasada de "compilación" separada de la ejecución. Es un intérprete línea por línea:

parser/parser.go
func (rt *Runtime) Parse(code string) {
    for _, line := range strings.Split(code, "\n") {
        rt.ParseLine(line)
    }
}

ParseLine mira el principio de cada línea ("space ", "let ", "when ", ...) y despacha a la función que sabe manejar esa forma. No hay look-ahead, no hay backtracking — cada línea se procesa, produce su efecto (crear un vector, registrar un transform, imprimir algo) y se olvida. El "programa" nunca existe como una estructura de datos completa en memoria; solo existe, una línea a la vez, el efecto de haberlo corrido hasta ahí.

Esto es lo que hace posible el REPL

Si hubiera una fase de "parsear todo el programa primero", un REPL interactivo necesitaría lógica especial para ir completando el árbol a medida que el usuario tipea. Como no la hay — cada línea se interpreta y se olvida — el REPL es literalmente ParseLine llamado una vez por cada Enter que presionás. Ver REPL.

El estado completo: Runtime

Si el intérprete no construye un AST, ¿dónde vive todo lo que el programa va creando? En un único struct de Go, Runtime — pensalo como "la memoria del intérprete": un conjunto de diccionarios, uno por tipo de cosa que un programa puede nombrar con let.

parser/parser.go (resumido)
type Runtime struct {
    // clásico
    Spaces     map[string]*core.Space
    Vectors    map[string]*core.Vector
    Scalars    map[string]float64
    Transforms map[string]*core.Transform
    LastCond   *core.Conditional

    // cuántico
    HilbertSpaces   map[string]*core.HilbertSpace
    QuantumStates   map[string]*core.QuantumState
    DensityMatrices map[string]*core.DensityMatrix
    Gates           map[string]*core.Gate
    Measurements    map[string]int
    Histograms      map[string]map[int]int
    Backend         core.QuantumBackend

    // persistencia
    Store       store.Backend
    Collections map[string][]*core.Vector

    // errores y estado de bloques multi-línea (ver abajo)
    LastError  *RuntimeError
    inTransform, inGate, inFor, inTry bool
    // ...
}

Cuando escribís let p1 = Personas[25, 40000], lo que pasa literalmente es: rt.Vectors["p1"] = core.NewVector(...). Un space va a rt.Spaces. Un hilbert va a rt.HilbertSpaces. No hay un namespace único compartido — p1 en Vectors y p1 en Scalars podrían, en teoría, coexistir sin chocar, porque cada map es independiente (en la práctica, el programa nunca reutiliza nombres así a propósito).

No hay scoping. No hay funciones con variables locales, no hay bloques que oculten nombres — todo let, en cualquier parte del programa (incluso dentro de un for o un try), escribe al mismo Runtime global. Es un espacio de nombres plano, como una hoja de cálculo: todo lo que alguna vez nombraste con let sigue vivo y accesible hasta que el programa termina (o hasta que otro let con el mismo nombre lo pisa).

Gestión de memoria: no hay

Esta es, probablemente, la pregunta que más te interesa: ¿quién libera la memoria? La respuesta corta: nadie, explícitamente — y eso es correcto, no un descuido.

LinLang está escrito en Go. Go tiene garbage collector (recolector de basura): cuando creás un valor con make(...) o un struct literal (&Vector{...}), Go lo reserva en el heap (memoria de larga duración, no la pila de la función), y el runtime de Go lo mantiene vivo mientras algo lo siga referenciando. En el momento en que ya nadie tiene un puntero a ese valor, el recolector eventualmente lo libera — vos nunca llamás a algo como free() o delete.

¿Cuándo "muere" un Vector?
Cuando ningún mapa de Runtime lo referencia más. Si hacés let p1 = Personas[25, 40000] y después let p1 = Personas[30, 50000], el primer vector deja de estar en rt.Vectors["p1"] (fue pisado) — si nada más lo apunta, en algún momento el GC libera esa memoria. Vos no hacés nada para que eso pase.
¿Y si cierro el programa?
El proceso termina, el sistema operativo recupera toda su memoria de un saque — igual que cualquier programa.
¿Hay memory leaks posibles?
Sí, de la única forma en que los hay en un lenguaje con GC: si algo queda referenciado sin que lo necesites más. El caso concreto en LinLang: Runtime.Vectors (y los demás mapas) nunca se achican solos — cada let nuevo agrega una entrada, y nada la borra salvo que otro let use el mismo nombre. Un programa muy largo con millones de let distintos acumula esas entradas indefinidamente. En la práctica no importa para scripts, y cmd/todo-server lo evita creando un Runtime nuevo por cada request HTTP (ver abajo) — el anterior, completo, queda sin referencias y el GC se lo lleva entero.
El patrón real: "Runtime desechable"

Mirá cmd/todo-server: cada endpoint HTTP hace rt := parser.NewRuntime(), copia los space/transform ya declarados del schema, corre dos o tres líneas de .lin, lee el resultado, y termina. Ese Runtime entero — todos sus mapas — queda sin ninguna variable de Go apuntándolo apenas la función retorna. El próximo ciclo del recolector lo libera entero, de una vez. No hay "limpieza" explícita en ningún lado del código — es la consecuencia natural de no guardar el puntero en ningún lado que sobreviva al request.

Inmutabilidad por convención, no por el lenguaje. Nada impide, en Go, mutar un Vector.Values[0] = 99 directamente. Pero ninguna función del lenguaje lo hace: Add, Scale, Project, la aplicación de un transform — todas construyen un []float64 nuevo con make y devuelven un *Vector nuevo. Es una disciplina que el código respeta, útil para razonar sobre el programa (un vector, una vez creado, no cambia bajo vos) — pero no es una garantía que el compilador de Go imponga.

Las estructuras de datos centrales

Cinco structs cargan con casi todo el peso semántico del lenguaje. Ninguno tiene métodos "mágicos" — son datos simples con funciones que operan sobre ellos (el estilo idiomático de Go, muy distinto a una clase con comportamiento encapsulado).

core.Vector — una entidad clásica

core/vectors.go
type Vector struct {
    ID      int64              // autoincremental, global al proceso
    Space   *Space             // puntero: NO copia el espacio, lo referencia
    Values  []float64          // slice — ver nota abajo
    Strings map[string]string  // solo dimensiones String; nil si no hay ninguna
}

Values es un slice de Go, no un array fijo — una cabecera liviana (puntero + largo + capacidad) que apunta a un bloque de memoria contiguo en el heap. Dos vectores nunca comparten el mismo slice subyacente (cada operación que "modifica" un vector hace make([]float64, ...) nuevo), así que es seguro pasarlos entre funciones sin miedo a que una mutación en un lugar aparezca inesperadamente en otro.

core.Space — un tipo, como lista de dimensiones

core/spaces.go
type Space struct {
    Name       string
    Dimensions []string
    Types      []DimType  // paralelo a Dimensions, por índice
}

Notá que Dimensions y Types son dos slices paralelos — Types[i] describe Dimensions[i]. Es una técnica común en Go cuando no hace falta un tercer struct "Dimension" con dos campos: más liviano, una asignación de memoria menos.

core.QuantumState y core.Gate — la versión compleja

core/hilbert.go, core/gates.go
type QuantumState struct {
    Space      *HilbertSpace
    Amplitudes []complex128   // Go tiene números complejos nativos
}

type Gate struct {
    Name     string
    Domain   *HilbertSpace
    Codomain *HilbertSpace
    Matrix   [][]complex128   // fila por fila — slice de slices
}

complex128 es un tipo nativo de Go (como float64, pero con parte real e imaginaria) — no hace falta ninguna librería externa para álgebra compleja básica. Matrix es un slice de slices: Matrix[i] es la fila i, cada una su propio slice independiente — no una matriz "plana" de una sola asignación. Para los tamaños que maneja el simulador (hasta unos pocos miles de amplitudes antes de que Gate.Apply se vuelva el cuello de botella — ver Referencia rápida), esto es simple y suficientemente rápido.

core.DensityMatrix

Misma forma que Gate (una matriz n×n de complex128) pero semánticamente distinta: no es un operador que se "aplica", es un estado (posiblemente mixto). Trace(), Purity(), PartialTrace(subDim) son sus operaciones propias.

Cómo funcionan los bloques con llaves

transform, gate, for y try son las únicas construcciones que abarcan más de una línea. Como el intérprete procesa línea por línea y nunca mira "hacia adelante", necesitan una forma de recordar en qué bloque están mientras acumulan las líneas intermedias. La solución es un par de banderas booleanas por tipo de bloque, más un struct "pendiente" que va juntando las líneas:

parser/parser.go
type Runtime struct {
    // ...
    inTransform bool
    pendingTx   *pendingTransform

    inGate      bool
    pendingGate *pendingGateDecl

    inFor       bool
    pendingFor  *pendingForLoop

    inTry, awaitingCatch, inCatch bool
    pendingTry  *pendingTryBlock
}

El flujo, para transform como ejemplo: la línea transform nombre: A x B -> C { pone inTransform = true y crea un pendingTx vacío. Cada línea siguiente, mientras inTransform sea true, no pasa por el switch normal de sentencias — ParseLine la intercepta primero y la agrega a pendingTx.mappings. La línea } dispara finalizeTransform(), que arma el core.Transform final a partir de todo lo acumulado y lo registra en rt.Transforms, y recién ahí vuelve inTransform = false.

Es el mismo patrón, cuatro veces, con datos distintos en el struct "pendiente". Y es exactamente este diseño el que hace que escribir un transform a lo largo de varias líneas del REPL funcione sin código adicional: cada Enter es una llamada más a ParseLine, y el estado inTransform/pendingTx sobrevive entre llamadas porque vive en el mismo Runtime de siempre, no en una variable local que se perdería.

La limitación que esto trae

Como cada tipo de bloque solo rastrea su propio par de llaves, ninguno sabe anidar otro bloque adentro — un for no puede contener un gate { ... }, por ejemplo. El cuerpo de un bloque es una lista plana de líneas, no un árbol.

Hardware y runtime distribuido

Backends y distribución

Del simulador ideal a hardware cuántico real, pasando por GPU, y de un solo proceso a un clúster de Kubernetes migrando qubits entre nodos por teleportación.

La interfaz QuantumBackend

Todo lo que ejecuta apply/measure implementa esta interfaz chica — el mismo rol que store.Backend cumple para persistencia, pero para QPUs:

core/backend.go
type QuantumBackend interface {
    Name() string
    Apply(gate *Gate, state *QuantumState) (*QuantumState, error)
    Measure(state *QuantumState) (outcome int, probs []float64, err error)
    SupportedGates() []string
    Topology() Topology
    NoiseModel() NoiseModel
}
Por qué el hardware real no "aplica" estados

Apply recibe un vector de amplitudes arbitrario como entrada. Eso tiene sentido para un simulador — es solo un array en RAM — pero ningún QPU real puede hacer eso: no existe forma física de "cargar" un vector de amplitudes arbitrario en qubits reales. Un QPU real solo sabe correr un circuito completo desde |0...0⟩ y devolver bits clásicos. Por eso SuperconductorBackend y TrappedIonBackend implementan QuantumBackend (así tipan correctamente y reportan su topología/ruido reales) pero Apply/Measure directamente devuelven un error — el camino real es la interfaz CircuitRunner, con un método Run(circuit, shots) que sí corre un circuito completo. Es una distinción que vale la pena entender: no es una limitación del código, es una limitación de la física.

Quién no está, y por qué

QuEra (Aquila) quedó deliberadamente fuera: es un dispositivo de simulación Hamiltoniana analógica (pulsos sobre átomos de Rydberg), no de puertas digitales — traducir un circuito de LinLang/Q a su formato requeriría un compilador puerta-a-pulso, un problema de investigación aparte. Ver la Hoja de Ruta de la monografía para el detalle completo de esta decisión.

Compilación: QIR, optimización, ruteo

Entre el circuito que escribís y el backend que lo ejecuta hay una representación intermedia — un DAG (grafo acíclico dirigido) de puertas, donde la dependencia entre dos nodos existe solo si tocan el mismo qubit:

core/qir.go
type QIRNode struct {
    ID     int
    Gate   *Gate
    Qubits []int
    Deps   []*QIRNode  // nodos que deben ejecutar antes
}

type QIRCircuit struct {
    NumQubits int
    Nodes     []*QIRNode
}

Dos puertas sobre qubits distintos son nodos independientes — el DAG es lo que permite que OptimizeCircuit y RouteCircuit razonen sobre qué se puede reordenar o combinar sin romper la semántica del circuito.

OptimizeCircuit
fusiona puertas adyacentes sobre el mismo qubit por multiplicación de matrices, y descarta pares que se cancelan (su producto da la identidad salvo fase global) — esto cubre H²=I, X²=I, etc. sin casos especiales por nombre de puerta.
RouteCircuit
inserta puertas SWAP cuando una puerta de 2 qubits cae sobre posiciones físicas no adyacentes, según la Topology del backend — heurística voraz (BFS del camino más corto), no el mínimo global de SWAPs (ese mínimo es NP-hard).

Primitivas de distribución

Cuatro piezas que, combinadas, hacen que "migrar un qubit a otra máquina" sea una llamada de runtime y no un proyecto de investigación aparte.

QuantumChannel

core/channel.go
type QuantumChannel interface {
    NodeA() string
    NodeB() string
    ShareBellPair() (*BellPair, error)
    SendClassical(from string, bits []int) error
    RecvClassical(to string) ([]int, error)
}

LocalChannel es la implementación de referencia — ambos extremos en el mismo proceso, análoga a MemoryStore para persistencia.

BellPool

Envuelve un QuantumChannel y pre-genera pares de Bell en un buffer, para que teleport no pague el costo de generación en el camino crítico. Implementa QuantumChannel él mismo — Teleport(psi, pool) funciona sin ningún cambio.

HilbertRegistry

El directorio de quién-tiene-qué: qué NodeID posee actualmente cada espacio de Hilbert nombrado. Register, Owner, Transfer, Local(nombre, nodo) — la pregunta que cualquier operación debe responder antes de decidir si corre localmente o necesita un QuantumChannel.

ScheduleCircuit

ScheduleCircuit(circuit, ownerOf, cluster) → []TeleportStep

El análogo distribuido de RouteCircuit, con teleport en el rol de SWAP — nunca puede ser SWAP, porque el no-clonación prohíbe mover un qubit entre nodos de cualquier otra forma. Para cada puerta de 2 qubits cuyos operandos viven en nodos distintos, inserta la teleportación necesaria.

Cada contenedor, un QPU — quantum-node

Un servicio gRPC real (cmd/quantum-node, definido en proto/quantumnode/quantumnode.proto) que envuelve un QuantumBackend local y lo expone por red: Apply, Measure, Info. core.RemoteBackend es el cliente — implementa QuantumBackend hablando ese protocolo, así que un scheduler distribuido puede tratar un contenedor remoto exactamente igual que un backend local.
